# DECISIONS — บันทึกการตัดสินใจ

รูปแบบ: **[Phase] หัวข้อ** — ตัดสินใจอะไร + เพราะอะไร

---

## [0] ธีมและชื่อเกม: เลือกทางเลือก B — ตำนานหิมพานต์ไทย, ชื่อ **HIMMAPAN GUARD / หิมพานต์การ์ด**
Blueprint เสนอ 2 ทาง (High Fantasy ทั่วไป vs ตำนานไทย) และแนะนำ B ไว้แล้ว — เลือก B เพราะแตกต่างทันทีในตลาดโลก,
การ์ดมอนสเตอร์เป็นผีไทยสนุกกว่า, และทำคอนเทนต์โปรโมตภาษาไทยได้เนียน ระบบทั้งหมดใช้ได้กับทั้งสองธีม 100% — เปลี่ยนแค่ผิว

## [0] แพลตฟอร์มแรก: เว็บ (Vite + Three.js) → ห่อด้วย Capacitor ภายหลัง
ตาม blueprint §13.1 iterate เร็วที่สุดและทดสอบด้วย headless browser ได้

## [0] ใช้ zod เป็น schema แทน JSON Schema ไฟล์แยก
schema เดียวให้ทั้ง type ตอน compile และ validator ตอน runtime — ลดโอกาสที่สองอย่างหลุดจากกัน
ถ้าภายหลังต้องใช้ JSON Schema จริง (เช่นให้ tool ภายนอกอ่าน) ค่อย generate จาก zod

## [0] npm workspaces (ไม่ใช่ pnpm)
โปรเจ็คแม่ (ShopDash) ใช้ pnpm อยู่แล้ว การใช้ npm ในโฟลเดอร์เกมทำให้ workspace สองชั้นไม่ชนกัน

## [0] เกมอยู่ใน `games/himmapan-guard/` ของ repo เดิม
ผู้ใช้ขอให้แยก branch ไม่ใช่แยก repo — จึงแยกเป็นโฟลเดอร์อิสระ (มี package.json/tsconfig/node_modules ของตัวเอง)
และเพิ่ม `games` ลง `exclude` ของ tsconfig แม่ เพื่อไม่ให้ `next build` ของ ShopDash ไป typecheck ไฟล์เกม

## [1] ราคาเป็นจำนวนเต็ม + fixed timestep 30 tick/วินาที
30 Hz ละเอียดพอสำหรับ TD (ศัตรูเร็วสุด 1.75 ช่อง/วินาที = 0.058 ช่อง/tick) และเบากว่า 60 Hz เท่าตัวตอนรันจำลองพันด่าน

## [1] ศัตรูเดินตาม waypoint polyline ไม่ใช้ A* หา path
ด่านออกแบบมือทุกด่านอยู่แล้ว → deterministic 100%, ไม่มีต้นทุน pathfinding ตอนรัน 1,000 ด่าน
แลกกับข้อจำกัด: เส้นทางต้องเป็นแนวตั้ง/นอน (validator บังคับ)

## [1] ทิศที่หันของฮีโร่มีผลแค่ภาพ ไม่กระทบการเล็งเป้า
Arknights ใช้ทิศจำกัดมุมโจมตี แต่บนจอมือถือมันทำให้ผู้เล่นใหม่หงุดหงิดโดยไม่ได้เพิ่มความลึกมาก
ถ้าจะเพิ่มทีหลังให้ทำเป็น modifier ของด่าน (Hard/Hell) แทน — บันทึกไว้ใน PARKING.md

## [1] ศัตรูล่องหนถูก "เปิด" อัตโนมัติเมื่อถูกบล็อค
สมเหตุสมผลเชิงกายภาพ (ปะทะตัวกันแล้ว) และกันสถานการณ์ตันที่ผู้เล่นไม่มีตัวเปิดเลยแล้วแพ้แบบไม่มีทางแก้

## [1] โบนัสเจาะเผ่า/ธาตุรับเป็น input ของ sim (`SquadEntry.raceBonus`)
sim ไม่รู้จักระบบการ์ด (Phase 6) แต่รองรับผลลัพธ์ของมันแล้ว — เมื่อถึง Phase 6 แค่คำนวณค่าจากการ์ดที่ใส่แล้วส่งเข้ามา

## [1] ปรับค่าศัตรูด้วยการรันจำลอง ไม่ใช่ความรู้สึก
ค่ารอบแรกทำให้ AI ชนะ 100% ทุกด่านแม้เลเวล 1 → ปรับ HP ×1.45 / ATK ×1.5 / DEF ×1.15 แล้วใส่ตัวคูณรายเวฟในด่านบอส
ผลลัพธ์: ด่านผ่านได้ที่เลเวล 1 / 8 / 10–15 ตามลำดับ (ดู `npm run balance`)

## [2] Sprite เป็น procedural canvas ชั่วคราว ไม่ใช่ไฟล์ภาพ
Phase 3 คือเฟส "โรงงาน sprite" ตัวจริง — Phase 2 ต้องพิสูจน์ระบบ billboard/atlas ให้ได้ก่อน
จึงเขียนตัววาดแบบ procedural ที่ผลิต atlas **รูปแบบเดียวกับของจริง** เพื่อสลับได้โดยไม่แก้โค้ด render

## [2] วาดจริง 5 ทิศแล้ว mirror เป็น 8 ทิศ
สูตรเดียวกับ RO — ประหยัดงานวาด 37% และเป็นข้อจำกัดที่ Phase 3 ต้องออกแบบตามตั้งแต่ต้น

## [2] UI เป็น HTML overlay ไม่วาดใน canvas
ตาม blueprint §13.1 — ทำเมนู/ตู้สุ่ม/หน้ารูนภายหลังได้เร็วกว่ามาก และได้ accessibility/ฟอนต์ไทยฟรี

## [2] หลอดเลือดคำนวณความสูงหัวจากชนิดร่าง (`spriteHeadFraction`)
ตอนแรกใช้ค่าคงที่ = ความสูงเฟรม ทำให้หลอดลอยเหนือหัวมากบนจอมือถือ (ตัวละครกินพื้นที่เฟรมไม่เท่ากันตามชนิดร่าง)

## [2] ปุ่มเลือกทิศหลังเลือกช่อง (ไม่ใช้ลากนิ้ว)
ลากนิ้วแบบ Arknights แม่นยากบนจอเล็กและชนกับการลากหมุนกล้อง — ใช้ปุ่ม 4 ทิศ + ปุ่มยกเลิกแทน

## [0] ปรับค่าอัพรูน base 120 → 380 หลังรันโมเดลเศรษฐกิจ
ค่าเดิมทำให้ผู้เล่นปิดเป้าหมายปลายเกมได้ภายใน 90 วัน (ครอบคลุม 101%) ซึ่งขัดกับ §11.2 ข้อ 3
ค่าใหม่เหลือ 41% = ประมาณ 7 เดือนของการเล่นทุกวัน ใกล้เคียงกับ Summoners War ที่ผู้เล่นปลายเกม "จนทองตลอดกาล"
