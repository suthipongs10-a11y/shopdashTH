# 01 — วิเคราะห์ความเป็นไปได้ (Feasibility)

> สรุปสั้น: **ทำได้** ส่วนระบบใส่หมวกแบบ RO เป็น**ส่วนที่ง่าย** (โค้ดไม่กี่ร้อยบรรทัด พิสูจน์แล้วใน `prototype/headgear-lab`)
> ส่วนที่ยากจริงคือ (1) ทำให้ภาพจาก AI **สม่ำเสมอ** ทุกทิศ ทุกเฟรม ทุกชิ้น และ (2) ส่วน **MMO** (เซิร์ฟเวอร์, ฐานข้อมูล, กันโกง, คอนเทนต์)
> ซึ่งต้องจำกัดขอบเขตให้ดีตั้งแต่แรก

## 1. Ragnarok Online ทำหมวกอย่างไร (สิ่งที่เราจะเลียนแบบ "กลไก" ไม่ใช่ภาพ)

RO เป็นแผนที่ 3D แต่ตัวละครเป็น **sprite 2D ซ้อนกันหลายชั้น (paper-doll)**:

| ชั้น | หมายเหตุ |
|---|---|
| ตัว (body) | ตามอาชีพ+เพศ มีแอนิเมชันหลายเฟรม (ยืน เดิน ตี นั่ง ร่าย ตาย) |
| หัว (head) | **หน้า+ทรงผมรวมเป็นภาพเดียว** แต่ละทรงผมคือ "หัว" หนึ่งชุด เปลี่ยนสีผมด้วย palette |
| หมวกบน / กลาง / ล่าง | 3 ช่อง: บน (หมวก), กลาง (แว่น), ล่าง (หน้ากาก/ของคาบปาก) |
| อาวุธ, โล่, ผ้าคลุม | ชั้นแยก ลำดับการวาดเปลี่ยนตามทิศ |

หลักการสำคัญที่ทำให้หมวกถูก:
1. **หัวแทบไม่มีแอนิเมชัน** หัวมีภาพแค่ต่อทิศ (8 ทิศ) แล้วแค่ "ขยับตาม" จุดคอของตัวในแต่ละเฟรม
   → หมวกหนึ่งใบใช้ภาพแค่ **ต่อทิศ** ไม่ต้องวาดต่อเฟรม (RO วาดจริง 5 ทิศ อีก 3 ทิศกลับภาพ)
2. **จุดยึด (anchor/attach point)** ทุกเฟรมของตัวบอกว่า "คออยู่ตรงไหน" ทุกภาพหัว/หมวกบอกว่า "จุดที่ต้องวางลงบนคออยู่ตรงไหน"
3. **ลำดับการวาด (draw order) ต่อทิศ** เช่น หันหลังแล้วแว่นต้องอยู่หลังหัว อาวุธต้องอยู่หลังตัว

→ ทั้ง 3 ข้อ implement ไว้แล้วใน `prototype/headgear-lab/index.html` (ฟังก์ชัน `drawChar`, ตาราง `ORDER`, `fit` ของไอเท็ม)

### ปัญหาที่ RO มีแต่เราแก้เพิ่ม: ผมทะลุหมวก
ทรงผมชี้ฟูแบบ Kaelrin ในภาพ concept ถ้าใส่หมวกแม่มด ผมจะทะลุออกมานอกหมวก เราจึงกำหนดให้ทุกหมวกมีค่า `hair`:

| `hair` | ความหมาย | ตัวอย่าง |
|---|---|---|
| `full` | ผมแสดงเต็ม หมวกวางบน "crown" (ยอดผม) ของทรงนั้น | มงกุฎ, ที่คาดหูแมว, ต้นอ่อน |
| `capped` | สลับเป็นทรงผมเวอร์ชัน "ยุบ" (ผมแนบ ไม่มีส่วนเกินด้านบน) | หมวกแม่มด, หมวกไหมพรม |
| `hidden` | ไม่วาดผมเลย | หมวกเกราะครอบทั้งหัว |

ต้นทุน: แต่ละทรงผมต้องวาด 2 แบบ (full + capped) ต่อทิศ คุ้มเพราะทรงผมมีจำนวนน้อย (เริ่ม 6–10 ทรง) แต่หมวกมีเป็นร้อย

## 2. ระดับความยาก (1 = ง่าย, 5 = ยากมาก)

| งาน | ยาก | เหตุผล |
|---|:-:|---|
| ระบบเลเยอร์ + หมวก 3 ช่อง + กลับด้านภาพ | **2** | ตรรกะชัด ทำเสร็จแล้วในต้นแบบ |
| เครื่องมือจัดตำแหน่งหมวก (fitting) | **2** | ทำแล้วใน lab: ขยับด้วยลูกศร + export JSON |
| ภาพจาก AI ให้สม่ำเสมอข้ามทิศ/ข้ามชิ้น | **4** | AI วาดมุมเดิมซ้ำไม่เป๊ะ สเกลเพี้ยน ขอบภาพสกปรก (ดู §4) |
| แอนิเมชันตัวละคร (เดิน/ตี) | **4** | AI วาดเฟรมต่อเนื่องไม่ได้ดี → ต้องเลือกเทคนิคที่เหมาะ (§3) |
| แผนที่ + การชนกำแพง + การซ้อนหน้า-หลัง | **3** | ภาพวาดฉากสวยแต่ต้องตีกรอบเดิน/บังเอง |
| เซิร์ฟเวอร์ realtime (เดิน, เห็นกัน, แชท) | **3** | ใช้ Colyseus ช่วยได้มาก |
| ต่อสู้, มอนสเตอร์ AI, ดรอปของ, เลเวล | **3** | ตรรกะเกมปกติ แต่ต้องทำฝั่งเซิร์ฟเวอร์ทั้งหมด |
| บัญชี, เซฟตัวละคร, กระเป๋า, เทรด, กันโกง | **4** | งานระบบล้วน ผิดพลาดแล้วเศรษฐกิจในเกมพัง |
| คอนเทนต์ (เควส, แผนที่, ไอเท็ม, บาลานซ์) | **4** | ไม่ยากทางเทคนิค แต่กินเวลาที่สุดตลอดอายุเกม |
| ดูแลเซิร์ฟเวอร์จริง (ค่าใช้จ่าย, ล่ม, อัปเดต) | **3** | เริ่มที่ VPS ตัวเดียวได้ |

**คำแนะนำขอบเขต:** เป้าหมายแรกคือ "MMO ขนาดเล็ก" — เมือง Mossbridge 1 เมือง + ทุ่ง 2 แผนที่ + ดันเจียน 1 แห่ง, 3 อาชีพ, รองรับ ~50 คนต่อแผนที่ ทำแบบนี้ได้ด้วยคนเดียว + AI ถ้าค่อย ๆ ทำ

ประมาณเวลา (ทำ part-time, เป็นการประเมินคร่าว ๆ):
- M0–M1 ต้นแบบเดินได้ หลายคนเห็นกัน ใส่หมวกได้: 3–6 สัปดาห์
- M2–M4 vertical slice (ตีมอน, เก็บของ, เลเวล, เซฟ): 3–5 เดือน
- เปิดทดสอบปิด: 6–12 เดือน (ขึ้นกับปริมาณคอนเทนต์)

## 3. เลือกเทคนิคแอนิเมชันตัวละคร (ตัดสินใจแล้ว: ทางเลือก B)

ภาพใน `03_Sprite_Atlas.png` เป็นสไตล์ **ลงสีละเอียดแบบ painterly** สวยมาก แต่ถ้าให้ AI วาด "เฟรมเดิน 8 เฟรม × 8 ทิศ" ทีละเฟรม
แต่ละเฟรมจะออกมาคนละหน้าตาเล็กน้อย พอเล่นต่อกันภาพจะสั่นกระพริบ ใช้ไม่ได้

| ทางเลือก | วิธี | ข้อดี | ข้อเสีย | ใช้เมื่อ |
|---|---|---|---|---|
| A. AI วาดทุกเฟรม | สั่ง sprite sheet เต็ม | ง่ายสุดตอนเริ่ม | ไม่สม่ำเสมอ ภาพสั่น | ไม่แนะนำ ยกเว้น effect |
| **B. Cutout rig (แนะนำ)** | ตัดตัวเป็นชิ้น (ลำตัว แขน ขา) ชิ้นละ 1 ภาพต่อทิศ แล้วขยับด้วยโค้ด (หมุน/เลื่อน/ยืด) | **สม่ำเสมอ 100%** เพราะทุกเฟรมใช้ภาพชุดเดิม, ใช้ภาพน้อย, เปลี่ยนชุดเกราะง่าย | การเคลื่อนไหวดู "นุ่มแบบตุ๊กตากระดาษ" ไม่ใช่วาดมือทุกเฟรม | **ตัวละครผู้เล่น, NPC, มอนสเตอร์** |
| C. 3D pre-render | AI ทำโมเดล 3D จากรูป → rig (Mixamo) → เรนเดอร์ 8 ทิศเป็น sprite ใน Blender | เฟรมต่อเนื่องจริง ได้ 8 ทิศฟรี | ต้องเรียน Blender, งานต่อชิ้นนาน | อัปเกรดภายหลัง ถ้าต้องการท่าทางสมจริง |

ต้นแบบใน lab ใช้ B แล้ว (ขาแยก 2 ข้าง + ลำตัว + หัว ขยับด้วย sin wave) ไม่ว่าเลือก A/B/C **หัวและหมวกเป็นภาพนิ่งต่อทิศเหมือนเดิมเสมอ**
ระบบหมวกจึงไม่ต้องรื้อเมื่อเปลี่ยนเทคนิคตัว

| ไฟล์ | ใช้อะไรได้ | ปัญหาที่พบ |

แก้ (1)–(3) ด้วยเครื่องมือ `tools/sprite_clean.py` แล้ว ผลลัพธ์อยู่ที่ `art/samples/` (ดู `_preview.jpg`):
ตัดเป็น 8 ไฟล์, ล้างขอบ, ทุกตัววางเท้าที่จุดเดียวกันบนแคนวาส 320×320

ข้อ (5) คือเหตุผลที่ต้องสั่งภาพชุดใหม่ตามสเปคแยกชิ้นใน `03-sprite-spec.md` ภาพเดิมยังมีค่าในฐานะ **reference สไตล์** ให้ ChatGPT

## 5. ความเสี่ยงหลักและวิธีลด

| ความเสี่ยง | วิธีลด |
|---|---|
| ภาพ AI แต่ละชุดสไตล์ไม่ตรงกัน | ใช้ "Style Block" เดียวกันทุก prompt + แนบภาพ reference ทุกครั้ง (`04-chatgpt-prompts.md`) + มี QA checklist |
| หมวกวางไม่พอดีหัว | ทุกชิ้นหัววาดบนแคนวาสแม่แบบเดียวกัน + จูน `fit` ใน Headgear Lab ค่าเก็บเป็น JSON ไม่ต้องแก้รูป |
| ภาพกลับด้านแล้วแสงผิดทิศ | กำหนดแสง **จากด้านบน-หน้า** (สมมาตร) แทนแสงจากซ้ายบน |
| ขอบเขตบานปลาย ("MMO ต้องมีทุกอย่าง") | ทำตาม milestone ใน `05-game-architecture.md` ทีละขั้น มี DoD ชัด |
| ค่าเซิร์ฟเวอร์ | เริ่ม VPS 1 เครื่อง (~5–10 USD/เดือน) รองรับหลักร้อยคนพร้อมกันได้ |
| ลิขสิทธิ์ | ใช้ "กลไก" แบบ RO ได้ แต่ห้ามใช้ชื่อ ภาพ เพลง ตัวละคร ไอเท็ม ของ RO; โลก Mossbridge เป็นของเราเอง |
